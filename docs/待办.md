## TODO-001　导入创建项目同步到书架，相同项目直接打开不重复导入

**状态**：待办（未动工）
**提出日期**：2026-10-15
**范围**：拆书导入链路 + 下载管理器交接链路 + 书架列表

### 需求原文

> 导入创建项目同步到我的书架，相同项目直接打开不重复导入

拆成三条可验收的子需求：

1. 导入（拆书 / 从下载管理器导入）成功创建的项目，要**自动出现在「我的书架」**里。
2. 若该项目**已在书架中存在**，则**直接打开现有项目**，不再新建。
3. 同一本书反复导入，**不产生重复项目**。

### 三、待定决策（动手前必须先定，否则实现方向会返工）

**D1　「相同项目」按什么判定？** 三个候选，各有取舍：

| 方案 | 判定键 | 优 | 劣 |
| :--- | :--- | :--- | :--- |
| A. 来源书 ID | `(user_id, source_book_id)` | 最准，同书必中 | 只覆盖下载链路；上传 TXT 没有 book_id |
| B. 内容指纹 | EPUB/TXT 正文 hash（或前 N 章 hash） | 覆盖两个入口 | 需落库 + 全量算一次 hash，几十万字的成本要评估 |
| C. 书名归一化 | `title` 去空白/去书名号/全角半角归一后比对 | 零改表，最快 | 同名不同书会误判（网文重名很常见）；改名重导会漏判 |

倾向：**A + C 组合**（下载链路用 book_id 精确命中；上传链路退回书名归一化并提示确认），
但这属于产品口径，需拍板。**未有结论前不动 G1/G2 的建表与查询逻辑。**

**D2　命中已有项目时，用户想「打开」的是哪个页面？**

- 项目详情 / 章节页（当前 apply 后跳的 `/project/{id}/chapters`）；
- 还是给一个中间提示「该书已在书架，是否覆盖导入 / 另存为新项目」。

**D3　命中时是否仍要跑拆书解析？** 复用项目 = 跳过全部解析，还是仍然解析但结果并入已有项目（即启用现有 `overwrite` 分支 `book_import_service.py:725`）。

### 三、待定决策

**D1　「人设」的更新口径 —— 谁有权改 `personality`/`background`/`appearance`/`traits`？**
这是本条最硬的问题。三个选项：

| 方案 | 说明 | 风险 |
| :--- | :--- | :--- |
| A. 分析直接覆盖 | AI 分析输出人设变化 → 直接写字段 | 人设是最需要稳定的东西，AI 每章重写会让角色漂移 |
| B. 只追加日志，**不自动改字段** | 日志记「第N章疑似人设变化：…」，由人**手动采纳**后才写入 | 安全，但 C1 名义上没"自动更新" |
| C. 混合 | `current_state` 类易变字段自动写；`personality` 类稳定字段只记日志待采纳 | 需明确划分两栏字段清单 |

倾向 C，但**必须拍板**：需求原文是「角色卡需要更新」，未说明更新到哪一层。

**D2　日志表的粒度** —— 一条日志记什么？

- 每个**字段**一条（field / old / new / chapter / source）→ 可精确 diff，条目多；
- 每个**角色每章**一条（含该章所有字段变化的 JSON）→ 条目少，diff 要 JSON 内比。

**D3　手动编辑日志的语义** —— 用户改了日志行，是：

- 只改**日志文字**（注释性质，不动角色字段）；
- 还是改日志时**联动回写角色卡字段**（即日志成为可编辑的真相源）。

第二种力量大但会引入"改日志导致角色卡变动"的链路，需确认。

**D4　日志是否可删/可否作为回滚依据** —— 若支持"从日志回滚到某章状态"，等于要存全量快照，成本量级不同。

## TODO-008　大纲应是对真篇内容的总结或预先处理，而非某段内容

### 需求原文

这条是**定位性/语义性**的需求 —— 指当前大纲的实际产出偏向"某一段内容的描述"，

1. **真篇内容总结** —— 对已完成正文的归纳（"这一章实际发生了什么"）；
2. **内容的预先处理** —— 对未写正文的规划（"这一章打算写什么"）。

### 一、现状核对（已读代码）

先说结论：**两种形态在系统里都已存在，但被混在同一个数据结构与同一套 UI 里，没有区分标识。**

#### 1. 数据层：只有一个 `Outline` 表，不区分"总结"还是"规划"

#### 2. 「预先处理」形态 —— 生成与续写

| 提示词 | 位置 | 任务描述 |

**这是"预先处理"的正当形态** —— 规划未来章节。粒度 = 一章一对象。

#### 6. `_build_chapters_brief` 只给标题不给内容 —— 上下文贫瘠

### 二、机理：为什么偏偏是这两张表

#### 1. 两张表是**运行时动态建表**，不走模型声明

它们**不在** `app/models/` 目录下，而是就地定义在 API 模块里：

| 表 | 定义位置 | `__tablename__` |
| :--- | :--- | :--- |
| `SourceTask` | `app/api/source.py:53` | `:56` `"source_tasks"` |
| `DownloadJob` | `app/api/ext_download.py:56` | `:67` `"download_jobs"` |

建表靠 lifespan 里的 `create(checkfirst=True)`：

```python
# main.py:150-152
from app.api.source import SourceTask
await conn.run_sync(
    lambda sync_conn: SourceTask.__table__.create(sync_conn, checkfirst=True)
)
# main.py:186-188
from app.api.ext_download import DownloadJob
await conn.run_sync(
    lambda sync_conn: DownloadJob.__table__.create(sync_conn, checkfirst=True)
)
```

外加幂等补列函数 `_ensure_source_task_columns`（`:55-80`）与
`_ensure_download_job_columns`（`:84-123`）—— 这**正是本工程自述的惯例**：
`download_manager_plan.md:30` 写明「建表惯例：lifespan 里 `create(checkfirst=True)` +
幂等补列函数，**不走 alembic**」。

#### 2. 而 `env.py` 的 metadata 只认 `app/models/`

`alembic/sqlite/env.py:22-30` 逐项导入模型：

```python
from app.database import Base
from app.models import (
    Project, Outline, Character, Chapter, GenerationHistory,
    Settings, WritingStyle, ProjectDefaultStyle,
    RelationshipType, CharacterRelationship, Organization, OrganizationMember,
    StoryMemory, PlotAnalysis, AnalysisTask, BatchGenerationTask,
    RegenerationTask, Career, CharacterCareer, User, MCPPlugin, PromptTemplate,
    BackgroundTask

```

`app/models/__init__.py` 的 `__all__`（`:25-59`）列了 33 项，
**`SourceTask` / `DownloadJob` 不在其中**（它们根本不在 `app/models/` 目录下）。

#### 3. 于是形成「双轨」

| 轨 | 建表方式 | 是否进 metadata |
| :--- | :--- | :--- |
| 主轨 | `app/models/` + Alembic 迁移 | ✅ |
| **副轨** | **API 模块内定义 + lifespan `create(checkfirst=True)`** | ❌ |

**Alembic 的 autogenerate 是"以 metadata 为准"来算差的**：
metadata 里没有 = "这个表不该存在" → 生成 `drop_table`。

#### 4. 触发命令

`scripts/migrate.py:94-113` `auto_migrate()`：

```python
def auto_migrate():
    # 1. 创建迁移
    if not create_migration("auto_migration"):        # :101 → :54 alembic revision --autogenerate
        ...
    # 2. 执行迁移
    if not upgrade_database():                        # :106 → :60 alembic upgrade head
        ...
```

`create_migration` 内部（`:54`）：

```python
cmd = ["alembic", "revision", "--autogenerate", "-m", message]
```

**生成 + 执行是连着的** —— `python scripts/migrate.py auto` 一条命令，
既生成含 `drop_table` 的迁移，又立即 `upgrade` **执行它**。
不是"生成后让人审阅"，而是**直接落地**。
